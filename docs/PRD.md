# Agent Workstation 产品需求文档

**版本**：v0.3（澄清后）
**日期**：2026-11-05
**状态**：草案，待评审

---

## 0. 一句话

以「工作台」为组织单元、以「任务」为调度总线、以「结构化板块」为共享记忆的多 Agent 协作系统。

## 1. 边界

### 做
- 一个人可以拥有多个项目；每个项目下挂多个**领域工作台**。
- 每个工作台按**插件**装配板块、阶段、Agent 编制与验收规则。
- 工作台内多个 Agent 可群聊协作；人可随时插话、接管、审批。
- 根工作台负责任务立项、派发、依赖、验收，并可调度各工作台的 Agent 干活。
- 所有产物、变更、运行、花费可追溯、可回放。

### 不做（v0.1 明确排除）
- 多租户、组织架构、团队 RBAC
- 插件市场与第三方插件运行时
- 外部系统集成（CRM、邮箱、浏览器自动化）
- 容器级代码沙箱（v0.1 用「本地执行 + 白名单 + 人工确认 + 目录锁定」代替）
- 移动端
- 多人实时协同编辑（CRDT）

### 不是
- 不是通用聊天客户端（群聊只是协作界面之一）
- 不是垂直行业软件（小说/销售只是插件实例）
- 不是纯自动化流水线（人在关键节点常驻）

## 2. 用户与形态

| 项 | 决策 |
|---|---|
| 首发用户 | 独立创作者、一人公司、独立开发者 |
| 后续扩展 | 3–15 人小团队（架构预留，不做界面） |
| 部署 | 本地优先（SQLite + 本地文件），可平滑迁到云端 |
| 人机关系 | 人是一等参与者（participant），非「旁观者」 |

设计约束：**所有实体从第一天就带 `workspace_id`**，即使 v0.1 只有一条默认记录。这样上团队时不需要改表。

## 3. 概念模型

| 概念 | 定义 | 关键性质 |
|---|---|---|
| Workspace | 租户/工作区 | v0.1 单条默认值 |
| Project | 一个项目（一部小说 / 一个销售周期） | 有目标、期限、预算 |
| Workstation | 工作台，树形结构 | 有 `parent_id`，可任意深度；UI 只暴露两级 |
| Plugin | 工作台类型定义 | 声明 schema / 工作流步骤 / 板块 / Agent 模板 |
| Block | 板块实例（人物设定、大纲……） | 绑定一个 Entity 类型 + 一个渲染器 |
| Entity | 工作台内的结构化条目（一个模块、一条 ADR、一个角色），由板块展示 | 有版本、可 diff、可提案 |
| Agent | 执行单元 | 属于唯一工作台；模型 + 提示 + 工具白名单 + 预算 |
| Participant | 参与者 | `human` 或 `agent`，共用权限与消息模型 |
| Task | 任务 | 归属工作台，有验收标准与预算 |
| Thread | 会话线程 | `task` 任务线程 / `review` 评审 / `discussion` 讨论（群聊）/ `dm` 私聊 |
| Proposal | 变更提案 | Agent 唯一的写入方式 |
| Artifact | 产物 | 只读、可跨台引用 |
| Stage | 阶段 | 任务的工作流位置，决定该任务上下文中激活的 Agent 与可写板块 |
| Run | 运行 | 单次 Agent 运行记录，含 trace / token / 成本 |
| InboxItem | 待处理项 | 阻塞、待审批、失败等需要人介入的条目 |
| KnowledgeSource | 知识库来源 | 用户显式导入，只读，带引用锚点 |

> 另有一类**系统实体**（`system:task` / `system:proposal` / `system:files`）：平台表以保留前缀 `system:` 暴露给面板绑定，插件不得定义 `system:` 开头的实体。

## 4. 不变量（系统必须始终成立）

编号便于后续写测试。

**I1 — 作用域封闭**
Agent 的上下文只能来自：自己所属工作台子树 + 祖先链的授权投影。兄弟工作台的任何内容不可见，除非通过父级中转的 Artifact 引用。

**I2 — 四权独立**
可见（observe）、提案（propose）、发言（speak）、调用（invoke）是四种相互独立的权利，不互相推导。其中 `invoke(scope)` 表示在该作用域内创建或派发任务、触发 Agent 的权利。默认：普通 Agent 自身工作台四权齐全；祖先工作台仅 observe（摘要投影）；子孙工作台可 invoke（仅以工作台为单位派发）+ observe（任务状态与 steward 回传）；speak 需 steward 身份或被显式授权。子级 Agent 对祖先**没有** invoke 权，只能通过 steward 回传结果，或用 `report_blocked` 上报。

**I3 — 提案制**
Agent 不得直接写共享 Entity。所有写入走 `Proposal`，由人、steward 或指定审查 Agent 合并。合并产生新版本，旧版本永久保留。例外：插件将实体 `writeMode` 设为 `direct` 时允许直写，但仍产生版本。

**I4 — 派发以工作台为单位**
根工作台的任务默认派发给 Workstation，由工作台内部决定执行者。派发时任务类型取自目标工作台插件的 `tasks`。直接指派 Agent 是显式的高级选项，需记录理由。

**I5 — 阻塞必须升级**
Agent 无法完成任务时必须产出结构化阻塞信息（缺什么、试过什么、需要谁决策），不得用猜测填充。系统将其送入上级收件箱。

**I6 — 预算硬约束**
任务、工作台、项目三级预算。超限即熔断，不允许「先跑完再说」。
（M0 仅 run 级熔断，token 上限取 Agent 或任务预算字段；三级预算 M1。）

**I7 — 全链路可审计**
每次 Agent 运行记录：输入上下文摘要、工具调用、产出、token、成本、耗时。可回放。

**I8 — 引用可溯**
Agent 使用知识库内容得出的结论，必须携带引用（来源 + 锚点）。无引用的断言在审查中视为不可信。（随知识库 M1 生效。）

## 5. 功能范围

### P0（v0.1 必须）
| # | 功能 | 验收标准 |
|---|---|---|
| 1 | 项目与工作台树 | 可建项目、挂载工作台、任意级 parent_node 正确路由 |
| 2 | 插件装载 | 从 `plugins/pm` 与 `plugins/dev` 读取 manifest，自动生成板块与 Agent 模板 |
| 3 | 板块渲染 | M0 至少 4 种：board（任务看板）、table（测试结果 / ADR）、tree（只读文件树）、diff（改动审阅）；doc / graph 随 novel 于 M2；preview 于 M1 |
| 4 | Agent 编制 | 从模板实例化，可改模型/提示/工具，可启停 |
| 5 | 群聊 | 工作台内多人（含人）多 Agent 会话，支持 @ 与结构化消息类型 |
| 6 | 任务 | 根台创建 → 派发到工作台 → 接单 / 拒绝 / 反提案（counter）→ 完成回传 |
| 7 | 提案与合并 | diff 展示、通过/驳回、自动生成新版本 |
| 8 | 收件箱 | M0：最简「待处理」列表（command_confirm / blocked / proposal_review / run_failed）；M1：严重度与通知 |
| 9 | 运行记录 | 单次运行的 trace 可查，成本可汇总 |
| 10 | 预算 | M0：仅单 run 熔断；M1：三级上限，超限熔断并通知 |
| 11 | 多模型路由 | M0：OpenAI 兼容 + Anthropic 两个 adapter，失败即报错进待处理；M1：Ollama + 降级链 |
| 12 | 知识库（最小） | M1：导入 md/txt → 分块索引 → Agent 可检索 → 结果必须带引用 |
| 13 | 受控代码执行 | 命令白名单 + 人工确认 + 超时 + 工作目录锁定；可跑 build / test |

> **M0 实现子集**（避免第一版就做 13 项）：**1 / 2 / 3 / 4 / 5 / 6 / 7 / 9 / 13 全量**，加上 **8（最小版）、10（仅单 run 熔断）、11（两个 Provider，无降级）**。
> 12 知识库顺延 M1，不阻塞主链路。

### P1（v0.2 = M2 + M3）
- 插件协议正式化 + novel 插件（剧本 B 验收）
- 任务级阶段门禁（不满足退出条件不能进入下一 stage）
- 跨台 Artifact 只读引用
- 群聊结论沉淀为「决策记录」回写板块
- 任务依赖与甘特视图
- 上下文自动压缩与检索
- Bundle 导入导出 + 官方方案库（5 个）
- 预设安装向导（依赖检查 + 配置体检 + 试运行）

### 非目标
见 §1。

## 6. 主流程剧本（端到端验收用）

### 剧本 A：开发工作台（M0 验收）

> **前置条件**：`agent-workstation` 的骨架已手工搭好（Vite + Hono + SQLite + 三栏），`pnpm build` 能过。
> 工作台的第一个真实任务必须基于已有代码——否则会陷入「产品还不存在，却要用产品开发产品」的循环。

1. 新建项目，挂载「全栈开发工作台」，绑定本地 git 仓库，声明构建与测试命令。
2. 插件自动生成板块：任务看板、改动审阅、测试结果、架构决策、文件树；Agent 编制为架构师 / 前端 / 后端 / 测试 / 审查，**五个模板全部参与**。
3. 在总台创建任务「给任务看板加状态筛选」，**限定在 `apps/web/src/components/board/` 单个 Module 内**，验收写成断言：`pnpm build` 通过、`pnpm test` 通过、Playwright 用例（以 command 形式执行）通过。
4. 派发给开发工作台。架构师接单，拆成两个子任务（筛选组件 / 状态同步，均在 `apps/web/src/components/board/` 内），创建内部群聊。
5. 实现者为 `frontend-dev` 的两个实例，平台在子任务指派时自动创建各自的 worktree 与分支；两个实例独立实现，各自提交改动提案。子任务随工作推进走过 stage：实现 → 测试。
6. 测试 Agent 跑 build 与用例（Playwright 用例作为 command 验收执行），生成 TestRun 作为验收证据，子任务推进到评审。
7. 审查 Agent 不共享实现者上下文，只读 diff 与验收结果，提出两条问题。
8. 实现 Agent 修订后重新提交，**审查通过且可执行验收通过后，平台按串行合并队列合并到主分支**，子任务进入合并并完成。
9. 总台任务自动标记完成，成本与耗时记入项目账本。

### 剧本 B：小说工作台（M2 验收）

> 林某是独立作者，正在写《长夜》。

1. 新建项目《长夜》，添加「小说工作台」，插件自动生成：人物、世界观、大纲、章节四个板块；人物设计师、剧情架构师、连贯性审查、文风润色四个 Agent 模板。
2. 她手填三条人物卡，剧情架构师通过提案补了一条世界观规则。
3. 在**根工作台**创建任务「完成第三章」，指定：字数 ≥ 3000、视角为林某、不得违背人物设定。
4. 任务派发给**小说工作台**。剧情架构师接单，任务按 `write_chapter` 的工作流推进 stage：构思（plan）→ 起草（draft），并创建内部群聊。
5. 进入审查（review）stage 后，连贯性审查 Agent 读提案时发现：新章节让主角做出了与人物卡「缺陷」冲突的选择，提交阻塞与证据。
6. 系统升级到根工作台收件箱。林某点开对比，选择**保留原设定**并补充一句说明。
7. 架构师据此重写提案，审查通过，合并为新版本；任务进入润色（polish）stage 后定稿。
8. 根台任务自动标记完成，成本记入项目账本。
9. 林某在运行记录里回看整条链路：谁在什么上下文下做了什么。

这个剧本覆盖了：插件装配、结构化板块、提案制、派发、群聊、阻塞升级、人工决策、版本、审计。

**M0 以剧本 A 验收，M2 以剧本 B 验收。**

## 7. 成功指标

### v0.1（dev，M0/M1 后校准）

| 指标 | 目标 |
|---|---|
| 从打开到派发第一个任务 | < 15 分钟（前提：已有仓库且已配好 key） |
| 单 Module 任务从派发到合并的 wall-clock | ≤ 30 分钟 |
| 提案一次通过率 | > 50% |
| 验收命令首次通过率 | > 60% |
| 人工干预率（需要人决策的次数 / 任务数） | 20%–40%（太低说明失控，太高说明没用） |
| 单任务成本 | 可预测，偏差 < 30% |

> 均为初始目标，M0 后用真实数据校准。

### v0.2（novel）

| 指标 | 目标 |
|---|---|
| 单章从派发到通过审查的 Agent 轮次 | ≤ 12 |
| 提案一次通过率 | > 60% |

## 9. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 群聊 token 平方级增长 | 成本失控 | 发言仲裁 + 结构化 handoff + 轮次上限 |
| Agent 在错误上下文里工作 | 产出不可用 | 强制经工作台派发；上下文装配集中管理 |
| 插件抽象过度设计 | MVP 拖期 | 先服务 1 个真实插件，协议随第二个插件反推 |
| 结构化板块限制创作自由 | 用户流失 | 保留自由文本板块（doc-editor）作为逃生口 |
| 提案制摩擦太大 | 用户嫌烦 | 低风险实体允许直写（配置项），高风险走提案 |
| 开发垂直竞争激烈 | 用户不买单 | 先做 dogfooding，内部价值独立成立 |
| 多 Agent 改同一仓库冲突 | 合并地狱 | 一 Agent 一 worktree，提案即 PR，串行合并 |
| 代码上下文成本过高 | 单任务成本失控 | Module 划分 + 检索装配 + 预算硬约束 |
| 任务级阶段与工作台视图割裂 | 用户找不到「现在该干什么」 | 看板按 stage 分列 + 任务卡显示 stage |

## 10. 附录 A：信息架构

| 路由 | 页面 | 核心职责 | 关键交互 |
|---|---|---|---|
| `/` | 项目总览 | 项目列表、最近活动、阻塞汇总 | 新建项目（可套模板）、进入 |
| `/projects/:id` | 根工作台 | 任务、里程碑、工作台列表、收件箱、全局群聊 | 建任务、派发、审批、处理升级 |
| `/projects/:id/ws/:wsId` | 领域工作台 | 板块、Agent 成员、内部群聊 | 编辑板块、发起讨论、审提案 |
| `/projects/:id/ws/:wsId/:panelId` | 板块全屏 | 单板块展开（关系图/长文档） | 批量编辑、图谱浏览 |
| `/projects/:id/tasks/:taskId` | 任务详情 | 契约、stage、子任务、提案、验收、运行 | 派发、推进 stage、查看验收证据 |
| `/agents` | Agent 模板库 | 已注册的 Agent 模板（与 ARCHITECTURE §8 目录一致） | 查看/调整模板 |
| `/runs/:runId` | 运行详情 | 上下文、工具调用、成本、结论 | 回放、从该点重试 |
| `/plugins` | 插件管理 | 已装插件、版本、默认配置 | 启用/停用、查看 schema |
| `/settings` | 设置 | 模型与密钥、预算、数据位置 | 配置 Provider、导出备份 |

**布局约定（IDE 形态）**

```
┌──────────────────────────────────────────────┐
│ 项目名 · 预算余量（M1）· 待处理/收件箱 🔔     │
├──────────┬───────────────────────┬───────────┤
│ 工作台树  │  主内容区（板块）      │ 会话/成员  │
│ 根        │  任务看板 / 里程碑     │ 群聊       │
│ └ 开发    │  改动 / 测试 / 文件    │ Agent 卡   │
│   （小说 M2）│                     │ 提案列表   │
└──────────┴───────────────────────┴───────────┘
```

**页面级要求**

- 任何页面 ≤ 2 次点击可达「收件箱」，否则阻塞会被忽略。
- 群聊必须能折叠成「结论卡片」，否则长期项目会被消息淹没。
- 任务卡片和任务线程上必须可见当前 stage，用户要清楚「现在该干什么」。

## 11. 附录 B：非功能需求

| 类别 | 要求 |

## 12. 附录 C：术语中英对照

| 中文 | 代码标识 | 说明 |
|---|---|---|
| 工作台 | `workstation` | 树形节点 |
| 板块 | `block` / `panel` | block = 工作台上的面板实例（视图配置），panel = 插件中的面板定义；实体不归属于 block |
| 实体 | `entity` | 工作台内的结构化条目，按「工作台 + 类型」归属 |
| 系统实体 | `system:*` | 平台表暴露给面板绑定的保留实体：`system:task` / `system:proposal` / `system:files`（只读、虚拟、来自 git 工作树） |
| 提案 | `proposal` | Agent 的写入方式 |
| 代表 | `steward` | 唯一有权向上发言的 Agent |
| 阶段 | `stage` | 挂在任务上的工作流位置，决定该任务激活的 Agent 与可写板块 |
