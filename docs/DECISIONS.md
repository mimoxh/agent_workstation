# 决策记录（Decisions）

> 用法：**已定**项变更需写明理由与影响面；**待定**项在开工前必须收敛，否则会以「实现时的隐式假设」偷偷固化下来，后面很难改。

---

## 一、已定

### D1 · 个人优先，架构预留团队
- **决策**：v0.1 面向单人，不做成员管理；但所有表从第一天带 `workspace_id`，`participant` 抽象为 `human | agent`。
- **理由**：团队功能会让 MVP 周期翻倍，但表结构后补代价极大。
- **影响**：暂不做邀请、角色、审批流；权限模型按「主体 + 作用域 + 权利」设计，天然支持多人。
- **复核点**：当出现第二个真实用户时。

### D2 · 通用工作台先行，`novel` 作验收样本
- **决策**：先做平台与插件协议，不做垂直定制；`novel` 插件负责证明协议成立。
- **理由**：过早绑定行业会做成行业软件。
- **影响**：协议设计以 PRD §6 端到端剧本为准绳；跑不通就砍特性，不加抽象。
- **风险**：没有第二个插件时容易过度设计——所以第二个插件要在 M2 尽早落地。
- **⚠️ 2026-11-05 修订**：验收样本改为 `dev`（M0），`novel` 于 M2，见 D13 / D14。

### D3 · Agent 能力边界：内容生成 + 内部工具
- **决策**：Agent 只能读写本工作台的结构化数据、发消息、建子任务；不访问外部系统，不执行代码。
- **理由**：安全模型、审计、凭据管理全部可以推迟。
- **影响**：工具集固定为内置工具；插件只能追加同作用域的工具。
- **复核点**：接入外部系统时需重做凭据与确认机制。
- **⚠️ 2026-11-05 修订（见 D13）**：`dev` 工作台必须执行构建与测试，原「不执行代码」不再适用。改为**受控执行**：命令白名单 + 人工确认 + 超时 + 工作目录锁定；容器沙箱仍推迟到 v0.2。

### D4 · 层级：任意级模型，两级 UI
- **决策**：`workstation.parent_id` 自引用；产品只暴露「根 + 领域台」两层。
- **理由**：模型通用不增加成本，UI 通用会增加认知负担。
- **影响**：权限与路由必须按树实现，不能硬编码两层。

### D5 · 人是一等参与者
- **决策**：`human` 与 `agent` 共用消息、成员、提及、权限模型；人可随时插话、接管、打断。
- **理由**：全自动流水线在创作与销售场景都不可靠，人的判断是关键路径。
- **影响**：群聊必须支持「人 vs agent」混合；任务可指派给人。

### D6 · 提案制写入
- **决策**：Agent 不得直接修改共享 Entity，只能提交 `Proposal`；低风险实体可由配置放行直写。
- **理由**：多 Agent 并发写同一板块必然冲突，且需要可追溯的「为什么改」。
- **影响**：`writeMode` 成为插件级配置；提案 UI 与 diff 是核心界面之一。

### D7 · 根工作台插件化（`pm`）
- **决策**：根节点也是一个 `workstation`，装配 `pm` 插件，仅多一个「全局作用域」标记。
- **理由**：避免为 root 写第二套布局、权限、消息。
- **影响**：路由与权限统一；`pm` 插件需要 `Task` 实体的特殊支持（跨台可见）。
- **⚠️ 2026-11-05 修订**：Task 以 `system:task` 被面板绑定，不再需要插件内 Task 实体，见 D16。

### D8 · 多模型路由
- **决策**：支持 OpenAI 兼容 / Anthropic / Ollama 三类 Provider，按 Agent → 模板 → 项目 → 全局优先级取配置，失败可降级。
- **理由**：国内可直连、可本地化、可换厂商；用户自带 key。
- **影响**：降级必须写进 trace 并在 UI 标注；Ollama 的 tool call 能力弱，需串行化。
- **⚠️ 2026-11-05 修订**：M0 只有 OpenAI 兼容 + Anthropic 两个 adapter，失败即报错；降级链与 Ollama 在 M1，见 D17。

### D9 · 本地优先存储
- **决策**：SQLite + 本地文件，schema 保持 Postgres 兼容。
- **理由**：零运维、隐私好、离线可用。
- **影响**：不做云同步；备份靠导出与快照。

### D10 · UI 形态
- **决策**：IDE 式三栏（工作台树 / 板块 / 会话），中文优先。
- **理由**：这个产品的信息密度高，聊天式单栏放不下。
- **影响**：小屏体验差，移动端明确排除。

### D11 · 模块化：工作台 = 模块组合
- **决策**：调度、知识库、记忆、审批、通知都是「模块」；工作台通过 manifest 声明启用哪些、用什么策略。
- **配置层级**：平台默认 → 工作台声明 → 线程覆盖。**工作台是默认值容器，线程才是执行单元。**
- **边界**：配置只能表达「选哪种已有策略」，不能表达「发明一种新策略」。后者必须写代码，不进 manifest。
- **用户体验**：不暴露裸参数，只暴露预设（preset）+ 少量开关。
- **影响**：manifest 增加 `modules` 与 `presets`；装载时做组合体检（lint）。

### D12 · 市场：先官方供给，再开放分发
- **⚠️ 2026-11-05 修订**：原「v0.1 内置 5 个官方 Bundle」改为下述节奏；5 个方案只基于 pm / dev / novel，sales、内容运营、研究综述类方案等对应插件存在后再做。
- **决策**：v0.1 无 Bundle；v0.2 内置官方方案库 + 文件导入导出；v0.3 才开社区提交；评分评论更晚。
- **分享单元**：Bundle = 插件引用 + 预设 patch + 可选示例数据 + 提示词，**不含用户真实内容**。
- **信任模型**：第三方插件必须**纯声明式**（无代码），只允许 L1/L2 级别。
- **理由**：插件能读数据、能声明工具，允许代码等于允许任意代码执行，供应链风险与审核成本都不可接受。
- **影响**：`manifest` 的 `handler` 字段仅第一方可用；第三方只能用内置工具。
- **复核点**：官方方案覆盖不了主流场景时，再考虑开放代码插件（需沙箱）。

### D13 · 首个垂直改为「全栈开发工作台」
- **决策**：M0/M1 的参照插件从 `novel` 改为 `dev`；`novel` 退为 M2 的第二个插件。
- **理由**：能 dogfooding（用产品开发产品本身）；验收可执行（build / test / 截图 diff）；提案制与 code review 天然同构。
- **后果**：代码执行进入 P0（修订 D3）；新增 git 集成与 worktree 隔离（平台托管，非工具）；新增 10 个工具（M0 做 8 个）与 2 种面板（`diff` M0 / `preview` M1）。
- **风险**：与 Claude Code / Cursor 正面竞争。但内部使用价值独立于市场竞争成立。
- **复核点**：M1 结束时评估——它是否真的能稳定推动这个产品前进。

### D14 · 版本与里程碑对齐
- **决策**：首个版本 = 根工作台（pm）+ 全栈开发工作台（dev）；`novel` 是第二个插件，M2 做，用剧本 B 验收；`sales` 推到 M2 之后，不进任何里程碑。
- **映射**：v0.1 = M0 + M1；v0.2 = M2 + M3；v0.3 = M4。
  - M0.1 手工骨架（Vite + Hono + SQLite + 三栏 + 一个能跑的板块，`pnpm build` 通过，git 有历史）；
  - M0.2 pm 根台最小版 + dev 工作台 + 派发 + 提案/合并 + 运行记录 + 受控执行 + 最小安全底线（D17）；
  - M1 完整收件箱 + 三级预算 + Ollama + 降级链 + 知识库（md/txt）+ visual 验收 + `capture_screenshot` + `run_tests`；
  - M2 插件协议正式化 + novel；M3 门禁自动校验 / 跨台引用 / 决策记录 / 上下文压缩 / 甘特 / Bundle / 安装向导；M4 团队权限 + 社区市场。
- **理由**：M0 依赖 novel 会让首个可验收版本同时验证「创作 + 协议」两件事，周期不可控。
- **影响**：PRD §8 里程碑表、成功指标按 dev / novel 拆表。

### D15 · 阶段挂在任务上
- **决策**：`workstation` 表删除 `stage`；`task.status` 是平台通用生命周期，`task.stage` 是插件定义的工作流位置，只在 in_progress / reviewing 期间推进。manifest `stages` 改为可选的工作流步骤声明，由 `TaskTypeDef.stages` 按序引用。
- **理由**：同一工作台里不同任务处于不同阶段是常态，工作台级阶段把它压成单线。
- **影响**：stage 决定该任务上下文里激活哪些 Agent、哪些板块可写；Requirement 改为带 `kind` 的联合类型在任务上下文求值；M0 只做手动/Agent 推进 + done 前必须通过可执行验收，自动门禁在 M3。
- **复核点**：M3 做自动门禁时复核 Requirement 联合类型的表达力。

### D16 · 系统实体，Issue 并入 Task
- **决策**：平台表可被面板绑定，命名用保留前缀 `system:`：`system:task` / `system:proposal` / `system:files`（只读、虚拟、来自 git 工作树）；插件不得定义 `system:` 开头的实体。dev 的 `Issue` 不再是实体，而是任务类型 `dev.issue` 的 Task；`Change` 复用 `Proposal` 同理。
- **理由**：平台抽象若能被复用，就说明它成立——这是验证提案制与任务模型的关键测试点。
- **影响**：pm 看板绑 `system:task`；dev 的 board 绑 `system:task`、changes 绑 `system:proposal`、files 绑 `system:files`；dev 实体只剩 Module / ADR / TestRun / Page。

### D17 · M0 安全底线前移
- **决策**：M0 实现 (1) 单次 run 熔断（§6.2 全部条件，token 上限仅 run 级）；(2) 最简「待处理」列表（复用 inbox_item，kind ∈ command_confirm / blocked / proposal_review / run_failed，无严重度排序与通知）；(3) OpenAI 兼容 + Anthropic 两个 adapter，失败即报错进待处理。三级预算、Ollama、降级链放 M1。
- **理由**：熔断与待处理是「敢让 Agent 跑」的前提，不能等到功能齐了再补。
- **影响**：PRD P0 #8/#10/#11 标注 M0/M1 分界；I6 加注 run 级。

### D18 · 四权模型
- **决策**：`Right = 'observe' | 'propose' | 'speak' | 'invoke'`，四项相互独立不推导；`invoke(scope)` = 在该作用域内创建或派发任务、触发 Agent 的权利。默认授权见 ARCHITECTURE §4.2；子级 Agent 对祖先没有 invoke 权，只能经 steward 回传或 `report_blocked` 上报。
- **理由**：propose 与 speak 分开后，「能发言评审、不能提改」的审查类 Agent（`reviewer`、`continuity-checker`）与「能提改、不进群发言」的后台 Agent 才能精确表达。
- **影响**：propose 类工具检查 `propose` 权；检查式见 PLUGIN-SPEC §13。

### D19 · 技术栈：Vite 前端 + Hono 本地服务 + AI SDK
- **决策**：Node 26 LTS + pnpm workspace monorepo。前端 `apps/web` 用 React 19.3 + Vite 8 + TanStack Router / Query；后端 `apps/server` 用 Hono 4.13 + @hono/node-server 2.x 常驻进程，HTTP API 与 Agent 运行时同进程托管；SQLite + better-sqlite3 + Drizzle 0.45.x；模型层用 Vercel AI SDK v7（`@ai-sdk/anthropic` + `@ai-sdk/openai-compatible`，M1 接入 Ollama 社区 provider）。
- **理由**：产品核心是长生命周期的 Agent 运行时（分钟级 run、子进程、worktree、串行合并队列、重启恢复、SSE），需要常驻进程托管；本地应用不需要 SSR。monorepo 把 domain 物理隔离，比约定更可靠。AI SDK 省掉 M0 两个手写 adapter，同时保留自己的循环与熔断语义（不依赖 SDK 的 agent 抽象）。不用 node:sqlite：Node 26 中仍是 Release candidate（Stability 1.2），且 26.11 刚把 `DatabaseSync` 改名为 `Database`。
- **未选方案**：B「Next.js 16 + 独立运行时进程」——Next 的请求模型不适合托管长时 Agent 运行、子进程和合并队列，dev 热重载会打断运行，且要承担它的升级节奏与安全补丁（2026-11 安全发布修复 7 个漏洞，多数与本项目用不到的缓存特性有关）；C「从一开始就做 Electron」——打包与 better-sqlite3 针对 Electron 的原生模块重编译成本会提前到 M0，改为演进路径（M3 之后视需要包外壳：系统钥匙串、原生文件夹选择器、单安装包）；Tauri 不考虑——运行时是 TypeScript，只能作为 sidecar 挂在旁边。
- **影响**：ARCHITECTURE §1 / §2 / §6.4 / §8 / §9 重写；剧本 A 的 Module 路径变为 `apps/web/src/components/board/`。
- **复核点**：Drizzle 1.0 GA 时评估升级；node:sqlite 转为 Stable 时评估是否去掉原生依赖；需要分发给非开发者时评估 Electron 外壳。

### D20 · 页面由业务对象驱动，不再跟随 designs 设计稿
- **决策**：三个核心名词各占一屏：**工作台**（组织：板块 + 团队脉搏 + 讨论）、**任务协作室**（调度：协作时间线 + 任务头 + 参与者）、**指挥台**（根工作台：需要你 + 任务流水线 + 项目经理对话）。`/projects/:id` 就是根工作台，指挥台是根台多出的一个板块，同一套外壳（D7）。`designs/` 保留为历史参考；令牌与颜色语义继续沿用。
- **理由**：设计稿把契约头和看板压在一屏，围绕的是任务状态，不是协作过程。产品最缺的是「看得见多 Agent 在协作」，中心内容应当是时间线和团队动态。
- **影响**：任务详情的五个 Tab 与右栏线程合并为时间线；独立概览页取消，内容并入指挥台；D10 的三栏形态保留，但每屏中心不同。
- **复核点**：M2 novel 插件落地时，看时间线对创作场景是否同样成立。

### D21 · Ollama 走 OpenAI 兼容端点
- **决策**：Ollama 用 `@ai-sdk/openai-compatible` 接其 `/v1` 端点，不引入社区 provider。
- **理由**：少一个依赖和一层升级节奏；工具按序执行由平台循环保证，不依赖 provider 能力。
- **影响**：修订 D19 中「M1 接入 Ollama 社区 provider」。
- **复核点**：遇到兼容端点缺失的能力时再评估社区 provider。

### D22 · 任务线程默认 moderated
- **决策**：dev 的任务线程默认 `moderated`，Agent 可以互相 @ 并被唤醒；「快速接力」预设把它改回 `relay`。修订 Q1 表里 `task → relay` 的默认值。
- **理由**：`relay` 下实现者遇到问题只能猜或上报，正是「多 Agent 退化成串行工序」的根因。成本由 `maxTurns` 和预算兜住，工作 run 里的消息不计入发言轮次。
- **影响**：发言调度从 scheduler 移到 `runtime/conversation.ts`；同一线程同时只有一个发言者。

### D23 · 阻塞先经 steward 分诊
- **决策**：`report_blocked` 先唤醒本台 steward，它用 `resolve_block` 在本台解除，或用 `escalate_block` 上送人；上报者声明 `decider=human`、steward 就是上报者、或调度器未运行时直接进收件箱。steward 跑完没给结果时平台自动上送。
- **理由**：状态机里 blocked → escalated 的语义是「超出本台决策权才上送」，全部直达人会让人工干预率失控，也让 steward 名不副实。
- **影响**：I5 的「不得悬置」由平台兜底保证。

### D24 · 结论卡回写提前到 v0.1
- **决策**：`record_decision` 与「沉淀为 ADR 提案」随协作内核一起做，不等 M3。
- **理由**：这是协作成果落到共享记忆的唯一通路；只复用已有提案流程，增量很小。
- **影响**：PRD P1「群聊结论沉淀」提前；自动回写与决策检索仍在 M3。

### D25 · 控制台为主界面，顶栏标签切工作台，左侧栏切功能
- **决策**：打开应用默认进**控制台**（`/`，跨项目：需要你、全部工作台概况、项目经理对话）。顶栏左侧是项目切换器，后面是「控制台」标签加当前项目的全部工作台标签（子台平铺，带父台名）。左侧栏随标签变化：控制台下是总览 / 需要我 / 各项目经理 / 项目 / 系统页；工作台下是**群聊**（工作台大群 + 每个活跃任务的任务页）、**功能**（manifest 板块）、**团队**（成员、设置）。工作台不带 `panel` 时显示大群，根台的大群就是和项目经理的对话。视觉改为文档式风格：浅色为主、跟随系统切深色，页面是图标 + 大标题 + 属性行。
- **理由**：D20 把指挥台做成根台的一个板块，跨项目的事没有归处，切工作台要先进树再找板块。标签 + 上下文侧栏让「在哪个台」和「看台里什么」各占一处。
- **影响**：修订 D20：指挥台内容并入控制台总览，根台不再多一个板块；收件箱在控制台汇总为「需要我」（`/inbox`），项目内收件箱保留。颜色语义不变：橙（accent）= 等人，蓝（cool）= 机器在动，bad / ok 同前；主按钮改用墨色（primary），不占语义色。原型在 `designs/aw-workbench/`。
- **复核点**：工作台超过 8 个时标签栏是否需要溢出菜单；任务页属性行在 novel 场景是否够用。

### D26 · 设计台是对话驱动的第三个插件，稿子是沙箱里的 HTML
- **决策**：新增 `design` 插件。设计稿用单文件 HTML 表达，存为普通实体；没有任务类型和阶段，人说一句设计师出一版；评论、旋钮、设计令牌都作用在 HTML 上。跨台交接走冻结的 Artifact，在 dev 台起草任务等人派发。
- **理由**：HTML 模型写得好、能交互、开发能直接参考，比自定义画布协议省下一整套编辑器。流程式的阶段门禁会拖慢试错，这个场景的审计靠版本历史就够了。实体复用让版本、回滚、实时刷新都不用再写。
- **影响**：稿子按不可信代码处理（无 same-origin 的 iframe + CSP，见 docs/PLUGINS/DESIGN.md）。新增面板类型 `canvas` / `tokens`；工具可声明 `resultLimit` / `largeOutput`。

### D27 · 测试台是任务之上的质量台，不接管开发台的测试阶段
- **决策**：新增 `qa` 插件，管用例资产、版本回归、不稳定识别、覆盖率、缺陷闭环和发布结论。开发台的 test 阶段和验收门禁不动。测试台不写仓库，改代码一律交接成开发台任务。结果由平台按 JUnit 报告解析，Agent 只能按 id 运行人审过的套件。
- **理由**：单任务门禁回答“能不能合并”，版本质量回答“能不能发”，是两个问题。开发台的状态机写死了 test-engineer 和 test 阶段，迁出来风险大、收益小。报告文件比标准输出可靠，JUnit 又是各语言通用的格式。
- **影响**：逐用例结果用专表 `qa_run` / `qa_case_result`，不用实体，历史查询才撑得住。新增面板类型 `quality`（`config.view` 分派）。详见 docs/PLUGINS/QA.md。

## 二、待定（按重要性排序）

### Q1 · 群聊的发言调度机制 【✅ 已收敛】

**先纠正一个直觉**：「自由发言」在工程上从来不是真的自由——总得有东西决定谁开口。区别只在于这个决定由谁做、花多少钱、能不能复现。

#### 四种策略

| | **自由发言** | **点名制** | **竞价（意图申报）** | **接力** |
|---|---|---|---|---|
| 谁决定发言 | 每个 Agent 自己判断 | moderator（人或 steward） | 仲裁器按打分选 | 任务图 / handoff |
| 每轮调用 | N 次完整调用 | 1 次完整 + 1 次决策 | N 次短意图 + 1–2 次完整 | 按交接计 |
| 5 Agent × 10 轮 token 量级 | ≈400k | ≈100k | ≈220k | ≈20k |
| 可复现 | 差（几乎无法复现 bug） | 好 | 中 | 好 |
| 节奏 | 快、乱 | 慢、稳 | 中 | 线性 |
| 适合 | 2–3 人头脑风暴 | 评审、审查、定稿 | 多人讨论 | 任务流水线 |
| 典型故障 | 刷屏、重复、烧钱 | moderator 成瓶颈 | 意图误判、冷场 | 没有讨论，只有产出 |

#### 各自的具体机制

**自由发言**
每条新消息后，所有激活 Agent 并行判断「我要不要说」。实现上几乎必须加一个轻量 router（否则就是 N 倍成本），所以它实际是「一个便宜的模型决定谁说话」。优点是涌现感好；缺点是顺序不可控、后发言者重复前者、上下文迅速膨胀。

**点名制**
一个 moderator 维护发言队列，逐个点名。可以是轮询、可以是固定复审顺序（作者 → 审查 → 决策）、也可以由人手动点。优点是成本确定、流程可靠、可复现；缺点是慢，且 moderator 是单点。

**竞价（意图申报）**
消息到达后，每个 Agent 先提交一句「我想说什么、为什么、优先级」，仲裁器按相关性 / 角色匹配 / 最近发言次数 / 剩余预算打分，选 1–2 个正式发言。成本介于两者之间，质量通常最好——因为它在说话之前就完成了筛选。

**接力**
不聊天。Agent A 完成后产出结构化 `handoff`，直接交给 B。成本最低、最可预测，但只适合有明确依赖链的任务，不适合需要反复拉扯的讨论。

#### 建议

**按线程类型选，不要全局一刀切**。线程上增加 `mode` 字段，`thread.kind ∈ task / review / discussion / dm`（「临时小群」= 不超过 3 个 Agent 的 discussion）：

| 线程类型 | 默认 mode | 理由 |
|---|---|---|
| `task` 任务线程 | `relay` | 有明确输入输出，聊天是浪费 |
| `review` 评审线程 | `moderated` | 顺序固定，便于追责 |
| `discussion` 讨论线程 | `moderated`（v0.1）→ `bidding`（v0.2 起） | 质量与成本的最优解 |
| `dm` 私聊 | 不调度 | 点对点无需仲裁 |

**v0.1 实现顺序**：可用的 mode 为 `relay` + `moderated`（简单、可控），`free` 作为开关保留但不做默认，`bidding` 是 v0.2。

**无论哪种都要有**：发言轮次上限、结论卡片（把讨论压缩成结构化结论）、以及「静默」能力（预算耗尽自动停）。

### Q2 · 项目模板 【✅ 已收敛】
v0.1 内置 1 个项目模板「开发项目」（pm + dev），自动挂载对应工作台并预置少量实体；更多模板随 v0.2 方案库。

**理由**：让个人用户从零配置实体、Agent 编制，成本太高，首次体验会崩。
**建议**：模板就是一个 JSON（工作台列表 + 预置实体 + 初始任务），不引入新概念。

### Q3 · 长期记忆与知识库 【✅ 已收敛：不做自动记忆，做知识库】

#### 两者不是一回事

| | 长期记忆 | 知识库 |
|---|---|---|
| 来源 | 系统从交互中自动沉淀 | 用户显式导入 |
| 内容 | 偏好、历史结论、决策 | 文档、资料、样例、规范 |
| 可信度 | 推断，可能错 | 事实，可引用 |
| 可编辑 | 难（散落各处） | 易（就是文件） |
| 失败模式 | 记错、悄悄影响输出 | 检索不到、切分错 |
| 用户感受 | 「它怎么知道这个？」 | 「我给的，它查到了」 |

#### 为什么不做自动记忆

自动记忆本质是一个**不可解释的隐式状态**。产品早期它是负债：

- 用户看到 Agent「莫名其妙记得」某件事会不安，且无法删除。
- 创作场景里错误记忆会污染稿件，且极难定位。
- 它和提案制、可审计这两个原则直接冲突。

**「记忆」这个需求用三种显式机制满足即可**：

1. **板块即记忆** — 人物设定、世界观就是记忆，改了就生效，看得见。
2. **决策记录** — 重要结论显式写下（`message.kind = decision`），可回写板块。
3. **会话摘要卡片** — 长会话压缩成结构化摘要，作为可查看、可删除的对象存在。

三者都满足「显式、可编辑、可删除、可追溯」。

#### 知识库设计

**作用域**：`project` 级（全项目可读）或 `workstation` 级（只本台可读）。跨台需显式授权，规则与 Artifact 一致。

**来源类型**：md / txt 与手工笔记（v0.1）；pdf / docx（v0.2）；网页快照（v0.2+）。

**处理管线**：

```
导入 → 文本抽取 → 分块 → 索引 → 检索 → 注入上下文 → 强制引用
```

- 分块优先按标题层级，其次按段落；512–1024 tokens，重叠 10–15%。
- 每块保留 `source_id` + 锚点（页码 / 标题路径 / 字符偏移），用于引用跳转。

**检索**：
- v0.1 用 SQLite FTS5 全文检索 + 关键词，零依赖，够用。
- v0.2 加向量（本地 embedding 或 API），与全文做混合排序（RRF）。
- **不要一上来就上向量库**：全文检索的可解释性更好，调参成本更低。

**引用是硬要求**：Agent 引用知识库内容必须返回来源与位置；无引用的断言在审查中视为不可信。这是抑制幻觉最有效的机制。

**UI**：知识库面板（上传 / 列表 / 预览）+ 结果侧栏 + 引用可点击跳原文。

**不进系统提示词**：知识库内容按需检索注入（RAG），不能全量塞进上下文。

#### 判据（很重要）

> 系统要**改**的 → 结构化实体；系统只**读**的 → 知识库。

小说：人物 / 大纲 / 章节 = 实体；参考资料 / 风格样例 = 知识库。
销售：客户 / 商机 = 实体；产品手册 / 话术 / 竞品资料 = 知识库。
