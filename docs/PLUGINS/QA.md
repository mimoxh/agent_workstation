# 质量（开发台，原测试工作台）

**版本**：v0.2（D32 起并入开发台，dev manifest 1.9.0）
**日期**：2026-11-08

> 独立的 `qa` 插件已删除，下面的能力都挂在开发台上（见 DEV §15）。老的测试工作台启动时自动并进它绑定的开发台。

---

## 0. 定位

开发台的测试阶段回答“这个任务能不能合并”，质量板块回答“这个版本能不能发”。两者不重叠：任务门禁不动，质量板块管任务之上的东西，包括用例资产、版本回归、质量分析、缺陷闭环和发布结论。

三条边界：

- 质量成员不写仓库。修缺陷、补自动化都生成开发任务（默认本台），走现有的 worktree、审查和合并流程。
- 结果由平台执行和解析，Agent 不能自报。
- Agent 只能按 id 运行人审过的套件，不能传任意命令。

开发台默认仍是任务看板；七个质量板块在侧栏「测试」分组里（板块声明 `config.group`）。

## 1. 板块

| 板块 | 做什么 |
|---|---|
| 质量总览 | 发布结论及原因、关键指标、通过率趋势、待处理事项、一键运行 |
| 测试运行 | 运行记录、运行详情（失败聚类、基线对比、逐用例、原始输出、实时输出）、套件配置与定时 |
| 用例库 | 手工和自动化用例，AI 草稿人审后入库，「生成自动化任务」起草开发任务 |
| 测试计划 | 面向版本：套件 + 手工用例 + 准出标准，手工逐条执行，签字冻结报告 |
| 缺陷 | 严重度、复现信息、状态流转，「生成修复任务」起草开发任务，回归后自动验证 |
| 不稳定用例 | 自动识别，历史条带，隔离和解除 |
| 覆盖率 | 总体和文件覆盖率、相对上次的变化、本次改动里的低覆盖文件 |

七个质量板块共用一个板块类型 `quality`，用 `config.view` 分派，渲染器在 `apps/web/src/components/qa/`。

## 2. 成员

| Agent | 职责 |
|---|---|
| 测试负责人 | 看现状、发起回归、起草结论摘要 |
| 用例设计 | 从需求和代码设计用例，只产出草稿；也能读设计交接快照（`read_design_snapshot`）起验收用例 |
| 失败分析 | 读失败和代码，分类并给证据，起草缺陷 |

都只在被 @ 时工作，界面按钮发一条 @ 消息，默认不自动花 token。三个 Agent 都没有 `apply_patch`、`run_command`、`propose_entity`。台的负责人是架构师；任务内写测试、跑测试仍由 `test-engineer` 负责。

## 3. 数据

配置和资产是实体：`TestSuite`、`TestCase`、`TestPlan`、`BugReport`、`TestQuarantine`。`TestSuite` 和 `TestQuarantine` 是 `writeMode: propose`。

高频结果用专表，实体是 JSON 扫描，撑不住历史查询：

- `qa_run`：一次运行。`config_json` 是发起时的命令快照，套件之后被改不影响这次。
- `qa_case_result`：逐用例结果。`case_key` 由套件、classname、name 哈希得出。每个套件保留最近 100 次的明细，运行摘要长期保留。

## 4. 执行

每个开发台一条串行队列，一个常驻的分离头 worktree（`<worktree 根>/<开发台>/_qa`）。每次运行：

1. `checkout --detach <sha>`，`clean -fdx -e node_modules`。
2. 锁文件变了才跑开发台配置的 `setup`。
3. 用现有 `runCommand` 执行（白名单、脱敏环境、沙箱）。需要人确认的命令、改依赖的命令和 `git` 一律不能作为套件。白名单除 Node 工具链外还有 `python` / `python3` / `pytest` / `go` / `gotestsum`（`python -c`、`python -m pip`、`go get` 这类一律拒绝）；用容器沙箱时镜像要自带对应工具链，默认断网装不了。
4. 读报告文件，不读标准输出（输出被截断到 32KB）。支持 JUnit XML（`pytest --junitxml`、`gotestsum --junitfile` 均产出），以及 `coverage-summary.json` 或 lcov。报告按不可信处理：路径限制在 worktree 内，20MB 上限，不展开 XML 实体。

运行中的标准输出经 `/api/live/qa:<runId>` 实时推送，运行详情页直接看；`live_*` 事件不走 /api/stream。

套件可配定时运行（`schedule`：off / hourly / every6h / daily，`schedule_at` 填 HH:MM 本机时间，daily 生效，缺省按 09:00）。平台每分钟检查一次，到点且没有排队中的运行才触发（trigger = `schedule`），效果等同 `auto_run`：跑在目标分支 HEAD 上、进总览和回归判定。

开发台验收可以引用本台的套件（acceptance `{ kind: 'qa_suite', suite: <id> }`，见 DEV §7）：平台以 trigger = `acceptance` 起一次运行，跑在任务分支上，通过与否回写任务验收结果。这类运行不进质量总览的最新判定、趋势和回归检测，只在运行列表里留痕（标签「验收」）。

判定规则：

| 情况 | 状态 |
|---|---|
| 有失败或错误用例 | `failed` |
| 报告里全部通过，退出码 0 | `passed` |
| 没有报告、报告为空、解析失败、超时 | `error` |
| 退出码非 0 但报告里没有失败 | `error` |
| 命令没能运行起来 | `error`，标记环境问题 |

服务重启时，残留的 `queued` / `running` 标成 `interrupted`。

仓库配置不重复：运行时读本台的 `devSettings`（仓库、目标分支、`setup`）；没绑定仓库时质量总览给出提示。

## 5. 分析

逻辑都在 `packages/domain/src/qa.ts`，纯函数。

- **错误指纹**：取错误第一行，抹掉数字、地址、哈希、路径后哈希。
- **基线**：同一套件上一次完成的运行，优先同分支。
- **不稳定**：同一提交结果不一致（一次就算），或最近 20 次里样本不少于 5、翻转不少于 3 次且翻转率不低于 30%。一次回归不算。
- **发布结论**：`unknown` / `ready` / `risk` / `blocked`。没跑完的套件、低于准出线的通过率、未关闭的 P0/P1、未通过的手工用例是阻断；不稳定用例、未执行的手工用例、覆盖率不足、各套件提交不一致是风险。隔离的用例不计入通过率。

结论只陈述事实，发布由人在测试计划里签字。阻断时放行必须勾选并写明原因。签字后在根工作台会话发一条 `decision`（结论、通过率、人工放行备注、关联里程碑），同时记 `qa_plan_signed` 事件；计划关联了里程碑时，根台的里程碑进度和 `project_status` 会带上这条测试结论，阻断或人工放行的未完成里程碑被标为有风险。

## 6. 缺陷闭环

`草稿 → 待修 → 修复中 → 待验证 → 已验证`，验证不过进 `重开`。

「生成修复任务」时，事实冻结进任务描述和 `qa_handoff` Artifact，在本台（项目里有多台开发台时可选别的）建 `dev.issue` 草稿，由人确认派发，和设计稿「生成实现任务」一致。

自动对账在运行结束时和仓库巡检节奏（`repo_watch`）上执行：开发任务完成进待验证，并记下验证起点；只有验证起点之后、目标分支上的运行结果才算数。没关联自动化用例的缺陷停在待验证，由人确认。

自动回归：套件开启 `auto_run`（或配了 `schedule`）后，目标分支的新提交只运行一次，平台外的提交也会触发。新增失败时进收件箱（`qa_regression`），并附上可疑合并：在上次运行之后合入、这次运行之前未回滚的开发任务（git 祖先判定），同时在每个可疑任务的会话里留言说明这次失败把它圈进了范围。

设计稿「生成实现任务」可以顺带请用例设计起草验收用例（见 DEV §14.5）：勾选后，开发任务创建的同时会在目标开发台会话 @用例设计 并带上冻结的 `design_handoff` 快照 id；用例设计用 `read_design_snapshot` 读快照（限同项目），按关键流程、交互状态、响应式断点、空态和错误态起草，经 `save_test_cases` 存为草稿由人审。

## 7. 现状与缺口

- 运行串行，同一开发台不并发；定时运行因此只保证「到点后尽快跑」，不保证准点。
- 实时输出只覆盖命令的 stdout/stderr，套件报告仍要运行结束才解析。
- 探索性 UI 测试没有做。
